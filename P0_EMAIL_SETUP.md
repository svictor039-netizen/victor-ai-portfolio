# Этап A / P0 — локальная реализация

## Текущий статус

Контакт: https://t.me/Rotciv_kld. Получатель писем: vslpk@inbox.ru.
Форма заявки и бриф используют один компонент, серверную проверку и один обработчик доставки.
Никакие реальные письма при разработке/тестах не отправлялись.

Сайт собирается в Astro SSR-режиме (`output: "server"`, адаптер `@astrojs/node`) и развёртывается на VPS как Node.js 22 runtime.
Сборка создаёт `dist/server/entry.mjs`; production-запуск: `node ./dist/server/entry.mjs`.
Фронтенд (Astro-сайт) и обработчик заявок (`server/lead-worker.mjs`) остаются отдельными компонентами: lead-worker разворачивается как самостоятельный Cloudflare Worker, а не как часть Astro runtime.

## Что требуется для включения

1. Аккаунт Unisender с включённым API-доступом и подтверждённым доменом отправителя `donskoe39.ru`.
2. Секрет `UNISENDER_API_KEY` с правом отправки; серверная настройка:
   - `UNISENDER_SENDER_EMAIL=info@donskoe39.ru`
   - `UNISENDER_SENDER_NAME=пос.Донское`
   - `UNISENDER_LIST_ID=1`
3. Виджет Cloudflare Turnstile для домена сайта: публичный sitekey и серверный `TURNSTILE_SECRET_KEY`.
4. Размещение `server/lead-worker.mjs` как Worker с конфигурацией `server/wrangler.jsonc`. Его HTTPS URL с путём `/api/leads` становится `PUBLIC_LEAD_ENDPOINT`.
5. В Worker: `ALLOWED_ORIGINS` — точные разрешённые origins через запятую, без путей и без wildcard.
6. Подтвердить и дополнить `/privacy/`: оператор, основания обработки, хранение/удаление, сторонние сервисы, порядок отзыва согласия. Затем выставить `LEAD_CONSENT_CONFIRMED=true` в Worker и `PUBLIC_LEAD_CONSENT_CONFIRMED=true` при сборке сайта.
7. В окружении сборки сайта: `PUBLIC_LEAD_ENDPOINT`, `PUBLIC_TURNSTILE_SITE_KEY` и `PUBLIC_LEAD_CONSENT_CONFIRMED`. Пересобрать после изменения этих публичных настроек.

Секреты хранить в секретах Worker, а не `PUBLIC_*`, исходниках или статическом Sites.
`UNISENDER_API_KEY` сейчас не задан; Worker возвращает 503, пока конфигурация неполна.
Формы показывают прямые контакты и недоступность отправки, пока публичные настройки не заданы.
Не вставлять ключи в чат, Memory или эту инструкцию.

## Доставка и ограничения

- Только POST JSON, лимит 32 KiB, проверка Origin, обязательных полей, длины и согласия.
- Honeypot и обязательная серверная проверка Turnstile с hostname/action.
- Получатель задаётся через env `LEAD_RECIPIENT`; пользователь не управляет заголовками письма.
- `ref_key` стабилен при повторе неизменённой формы в той же вкладке (основан на `requestId`).
- Ошибки/таймауты не выдают успех; данные остаются в форме. Персональные данные не пишутся в console, localStorage или URL.
- Успех означает принятие письма почтовым API, а не доказанную доставку в inbox. Проверка реального получения и папки спам нужна после настройки и отдельного разрешения на пробное письмо.
- До подключения провайдеров end-to-end доставка не проверена. Автотесты используют только моки.
- Telegram открывает личный контакт; mailto открывает почтовый клиент и не считается автоматической отправкой формы.
- Перед публичным включением подтвердить применимость выбранных провайдеров к обработке данных. `/privacy/` — явно обозначенная заготовка, не утверждённая политика.

## Проверки

Релевантные серверные тесты: `node --test server/lead-worker.test.mjs`
Затем `npm run check` и `npm run build`.
После настройки: отдельная проверка валидной заявки/брифа, отказа проверки, отказа email API и получения письма.
