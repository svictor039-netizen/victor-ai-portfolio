MCP подтвердил точные имена, типы, число файлов и объявленные npm-зависимости. Описания назначения получены из списка registry. Дополнительно прочитан публичный [JSON Card Flip](https://kokonutui.com/r/card-flip.json) для проверки реализации. Код только прочитан, не сохранён и не запущен в проекте.

В выдаче списка поле Add command отображалось как `[object Promise]`. Это дефект отображения команды, не ошибка чтения каталога. Команды добавления не использовались.

## Отдельная оценка Card Flip

**Компонент найден и проверен. Для основных проектных карточек в исходном виде не рекомендован.**

Что реально видно в исходном коде [card-flip.json](https://kokonutui.com/r/card-flip.json):

- React `useState`, импорты из `lucide-react` и локального `@/lib/utils`.
- Пропсы: title, subtitle, description, features. Отдельного image, href, статуса проекта и метрики результата нет.
- Переворот управляется `onMouseEnter` и `onMouseLeave`; самостоятельных click/focus/keyboard-обработчиков переворота нет.
- Wrapper — `div`; на нём нет keyboard-триггера. Обратная сторона содержит button без обработчика действия и без URL.
- Фиксированная высота 320 px, максимальная ширина 280 px; описание ограничивается двумя строками. Для русскоязычного кейса это тесно.
- Обе стороны находятся в DOM, скрытие выполнено через CSS backface; нет переключения inert/aria-hidden сторон. Влияние на порядок фокуса требует проверки.
- Есть `motion-reduce:transition-none` для переворота и отключение декоративной анимации; это плюс. Остальные переходы требуют отдельной проверки.
- Присутствует `<style jsx>`: совместимость с будущим стеком и обработчиком стилей нужно установить отдельно. Нельзя считать компонент одинаково готовым для любого React/Astro-проекта.

Для карточки доказательства пользователь должен сразу видеть, что сделано, в каком статусе, какую роль выполнял автор и чем подтверждается результат. Hover-переворот прячет этот слой и делает взаимодействие зависимым от устройства. CSS reduced-motion не решает проблему keyboard/touch-доступа.

Если позже нужен именно Flip: лицевая сторона сохраняет все ключевые факты и обычную ссылку на кейс; оборот содержит только необязательные детали; явная кнопка работает с touch и клавиатурой; невидимая сторона исключается из фокуса; сохраняется статичная версия при reduced-motion. Это уже адаптация компонента, а не готовое решение из registry.

## Приоритеты для следующего этапа

1. Рассмотреть **gradient-button** и **smooth-tab**, если они улучшают уже определённый пользовательский сценарий.
2. **Bento-grid** — лишь при наличии материала, который выигрывает от неодинаковых размеров блоков; обычная сетка для сравнения кейсов может быть лучше.
3. **Smooth-drawer** — после определения мобильного сценария контакта.
4. **Action-search-bar** — когда в каталоге станет трудно ориентироваться вручную.
5. **AI-prompt / ai-text-loading** — только вместе с настоящим AI-сервисом и проверкой качества.
6. **Card Flip** — необязательный эксперимент, не основа портфолио.

Выбор компонентов не фиксирует React или Next.js как стек Victor. Если выбранная архитектура проще без React-интерактивности, библиотека не должна диктовать платформу.
